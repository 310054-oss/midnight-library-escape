# 開發經驗

## 範圍

以下經驗適用於小型、繁體中文、以瀏覽器為主的解謎遊戲與 GitHub Pages 靜態網站；遇到多人連線、持久化進度或大型內容管理需求時要重新評估架構。

## 記錄

- 從聊天得知使用者想做「密室逃脫遊戲」，未指定平台、世界觀或框架。以容易分享、免安裝、低維護作為預設，採原生 HTML/CSS/JavaScript 靜態網站。
- 首章採一個明確主題與短流程，先確保探索、線索、解謎、成功回饋構成閉環，再新增內容。
- 文字線索要互相補足，且遊戲內要能查看線索，避免玩家點錯後失去重要資訊。
- GitHub Pages 適合純靜態遊戲；以 GitHub Actions 產生 artifact 並部署，可避免手動上傳與分支設定漂移。

- 把公開部署目錄獨立放在 `site/`，workflow 只上傳該目錄，可避免把知識文件和維運設定一同公開。此做法適用於要在同一 repo 保存內部開發文件與公開靜態網站的情況。
- 首章的解謎驗證：顏色順序由值班簿給出（紅、藍、黃、綠），掛畫給出各色數量（3、1、4、2），合成密碼 3142。錯誤密碼應保留在輸入框並指出可回查的線索，讓失敗可恢復。適用於短流程、可用多條線索拼合的初章。
- GitHub Pages 官方工作流程目前採 `actions/checkout@v6`、`actions/configure-pages@v5`、`actions/upload-pages-artifact@v4`、`actions/deploy-pages@v4`；部署 job 需 `pages: write` 與 `id-token: write`。每次新增部署功能時應先核對官方文件版本。

- 建遠端 repo 前先檢查 `gh` CLI 與 Git Credential Manager 的 GitHub 帳戶。若兩者都沒有已授權帳戶，先完成本地可做的實作、驗證與提交，再請使用者完成 GitHub 登入；不要把認證祕密寫入專案、終端輸出或知識文件。此經驗適用於所有需要推送到使用者 GitHub 的工作。

- 第二間房沿用同一個線索筆記與密碼鎖互動，但用章節狀態區分進度；切換房間時保留舊線索、只計算當前章節的進度，讓跨房間線索仍可回看。適用於無伺服器的短篇連續解謎。
- 結局對話框若有內部標題，外層就不要再輸出空白或重複 id 的標題；讓 `aria-labelledby` 指向唯一且可見的標題。適用於共用可變內容的對話框元件。
- 手動 smoke test 依序覆蓋：三間房的線索收集、正確密碼連續通關、錯誤密碼提示、章節切換、歷史線索保留及從頭重新開始。長篇解謎若要擴充，應繼續涵蓋跨章節狀態而非只測單一房間。
- 三房間的短篇流程可共用一份線索筆記和同一種密碼鎖，但房間切換要重設當前解鎖狀態，並只把當前房間線索計入進度。這適合無帳號、單次遊玩的線性密室。
- 需要聲音時可用 Web Audio API 合成短提示音，音訊只在玩家解鎖成功後播放，並提供清楚可操作的靜音開關；`prefers-reduced-motion` 可在 CSS 集中關閉轉場與動畫。這適用於不想依賴外部音檔的小型網頁遊戲。
- 互動物件使用至少 44px 的可點擊目標，房間舞台以有標籤的 `role="group"` 包含多個按鈕，避免把可操作子元素藏在純圖片語意下。適用於同時有點擊熱區與螢幕閱讀器使用者的探索畫面。
- GitHub connector 的 OAuth 連線不會自動登入瀏覽器，也不一定提供建立 repository 的操作。先檢查 connector 的實際操作與瀏覽器登入狀態；需要登入時讓使用者自行完成，不要自動化登入表單。適用於透過 connector 與瀏覽器混合完成 GitHub 發布的任務。
- 若 GitHub connector 有內容/commit API 但沒有 `git push` 或 repository 建立操作，可用瀏覽器建立空 repository，再透過 Git Database API（blob、tree、commit、ref）把本機最新樹寫入 `main`。這會保留初始化 commit，但不會自動搬移本機完整 commit 歷史；適用於仍需上傳完整版本且本機 Git 認證無法使用的情況。
- Actions 的 Pages workflow 顯示成功，仍需另外打開預期的 `owner.github.io/repository/` hosted URL 確認頁面實際載入；接著用瀏覽器逐章操作線索、門鎖與結局，才可把 hosted smoke test 記為完成。適用於純靜態 GitHub Pages 專案的發布驗收。
- 小型線性解謎的 hosted 端到端驗證可記錄每章線索如何組合成密碼、章節切換是否保留歷史筆記，以及最終結局是否到達；這能比單看 HTTP 或 workflow 成功提供更強的玩家流程證據。適用於無後端、跨章節共享狀態的瀏覽器遊戲。
- 桌面瀏覽器能通關不代表手機觸控與窄螢幕已驗證。路線圖應將真機版面/觸控檢查和真實玩家理解度回饋分開追蹤，並保留未完成狀態直到取得實際裝置或玩家證據。適用於響應式互動網站與遊戲發布。
- 瀏覽器的 390px、320px viewport 可快速檢視響應式斷點、直向捲動與觸控熱區密度，但仍是桌面模擬，不能當作手機瀏覽器、虛擬鍵盤或實體觸控的驗收證據。適用於先行篩出窄版排版問題，再安排真機 smoke test 的網站迭代流程。
- 邀請新玩家測試解謎時，使用不含答案的任務說明和固定觀察問題，記錄玩家原話、推理、卡點與是否受提示，再將推測和觀察分開整理；匿名化並只留改善所需資訊。適用於小型遊戲的可用性測試，降低觀察者提示造成的偏差。
- 模態對話框除了開啟時聚焦內容，也需用 Tab/Shift+Tab 限制焦點留在對話框內，關閉後把焦點還給觸發按鈕；若操作會切換內容並移除原按鈕，則應把焦點移到新內容中的第一個操作項目。適用於動態單頁介面與鍵盤/螢幕閱讀器操作。
- 對單頁遊戲做焦點管理 smoke test 時，至少覆蓋只有一個可操作按鈕的線索對話框、多控制項的密碼對話框、正反向 Tab、Escape、章節切換和從頭再玩。成功提交密碼時焦點會先離開輸入欄再打開結局對話框，重玩與切章則必須聚焦到新場景仍存在的熱區；適用於由同一個動態容器呈現不同對話框和遊戲章節的介面。
- 場景中的純裝飾圖形、星點、氣氛符號可用 `aria-hidden="true"` 排除於輔助科技閱讀；可操作熱區應以簡短且明確的 `aria-label` 命名，並將僅供視覺辨識的符號隱藏。保留場景群組的整體描述及可操作控制，避免清理朗讀雜訊時一併移除必要上下文。適用於以 CSS/HTML 插畫呈現、互動按鈕另行疊放的探索場景。
- 完成標記後，應檢查實際部署頁的輔助樹，而非只讀本機原始碼；小型 UI 元素（例如按鈕箭頭、計時裝飾）也可能產生多餘朗讀。此檢查可確認真實發布版本有套用變更，並適用於靜態網站部署後的無障礙驗收。
- 單頁介面切換時，焦點管理要涵蓋首次進入、後續章節切換和重置三種入口；隱藏目前焦點所在的畫面會讓鍵盤操作位置失去脈絡。首次進場宜將焦點移到新畫面第一個操作項目，適用於以隱藏/顯示區塊切換的單頁遊戲或精靈流程。
- 驗證單頁畫面切換的焦點時，除了查看輔助樹，也要觸發切換並確認瀏覽器回報的實際焦點落在新畫面的第一個可操作控制；這能抓到程式外觀正確但焦點仍停在隱藏舊畫面的問題，適用於首次進入、切章、關閉對話框和重置流程。
- 以 CSS Grid 置中的對話框，即使設定 `width: min(100%, ...)`，也可能被 grid 項目的自動最小尺寸依內容撐寬。窄螢幕的 grid 子項加上 `min-width: 0` 與 `max-width: 100%`，並用實際視窗查看長文字和表單按鈕是否完整可見。適用於置中在 grid/flex 容器內且含表單或長文的響應式對話框；桌面視窗模擬仍不能代替手機實機驗收。
- 觸控熱區在窄視窗下可能因 breakpoint 位移而重疊，即使每顆按鈕都達到最小尺寸。逐章收集按鈕矩形並檢查交集，再以實際截圖確認，適用於固定插畫舞台上多顆絕對定位熱區的遊戲；交集檢查只作桌面窄視窗篩查，真機觸控仍需實機操作。
- GitHub Pages workflow 若 deploy job 回報找不到 `github-pages` artifact，先看該次 run 的 Artifacts 區是否已產生 artifact；若建置端確有產物而部署查詢失敗，記錄為部署階段問題並重試一次新 run，再以部署成功和 hosted 頁面版本共同驗收。適用於 Pages workflow artifact metadata 偶發查詢失敗的排查；只有 deploy job 成功不能取代實際頁面檢查。

## 之後每個階段

- 做完功能後記下可重用的設計決定、踩坑、適用範圍。
- 將完成項目打勾，並把未完成工作依玩家體驗優先級排序回填到 `knowledge/plan.md`。
